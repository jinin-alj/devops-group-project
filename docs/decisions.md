# Architecture Decision Records

## ADR-1: Two-service architecture

**Context:** The product has wardrobe CRUD and usage/analytics concerns.

**Decision:** Keep clothing CRUD and persistence in the wardrobe service. Keep wear history and derived wear statistics in the outfit service.

**Alternatives:** A single application and database would be simpler, but it would not meet the required split and would make partial failure less observable.

**Consequences:** Services communicate over HTTP and can be deployed independently. The outfit service stores item IDs, not duplicated item data.

## ADR-2: Partial failure

**Context:** The outfit service needs wardrobe item data for cost-per-wear and unworn calculations.

**Decision:** Calls from the outfit service use a 3-second timeout. Network, timeout, and wardrobe HTTP failures return HTTP 503 with `wardrobe unavailable, try again later`.

**Alternatives:** Long synchronous calls could hang requests. Caching may hide stale data but would complicate ownership and invalidation.

**Consequences:** Wear logging remains independent because it stores only item IDs. The wardrobe service's CRUD remains usable while outfit statistics are unavailable.

## 1. Deployment and pipeline

**Date:** 2026-11-24  
**Owner:** Salome Shioshvili

**Context**  
The brief requires a one-time Azure setup that is scripted or written as IaC, then every merge to `main` must deploy itself. Nothing should be changed by hand in Azure after that. The group resource group is `rg-sdd-3b-g7` in the subscription "Azure Simple IE Instituto de Empresa, S.L.". The professor provides a managed identity for the pipeline instead of a service principal with a secret.

**Decision**  
- One-time setup is an Azure CLI script (`infra/setup.sh`), run with `CLASS=3b GROUP=7`.
- CD is a GitHub Actions workflow (`.github/workflows/cd.yml`) that runs CI, pushes both images to GHCR tagged with the commit SHA, updates both Container Apps, checks `/health`, then deploys the UI to Static Web Apps with Azure URLs written into `ui/config.js`.
- The pipeline logs in with OIDC as the managed identity `sdd-3b-g7-github` (federated credentials for `main`, including the numeric-ID subject form). GitHub stores only `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` — no password.
- Database passwords are generated by the setup script and stored only as Container Apps secrets, never in the repository.

**Alternatives**  
- Bicep or Terraform for the setup (credited, but the CLI script is enough and matches Assignment 2).
- A service principal with a client secret (rejected: the course switched to managed identity / OIDC).

**Consequences**  
- Anyone with access can reproduce the Azure setup from a clean machine.
- The first image push may need the GHCR packages set to public so Azure can pull them without a registry password.
- If `azure/login` fails with `AADSTS700213`, compare the subject in the error with the federated credentials and add the missing form.

## 2. Frontend: static browser UI

**Date:** 2026-11-24
**Owner:** Nikita

**Context**
The product needs item CRUD, wear logging, and outfit statistics while remaining
deployable as plain files from Azure Static Web Apps. The browser must continue
to call both services directly and show a useful message when either service is
unavailable.

**Decision**
Keep the UI as a static `index.html` that loads the existing `config.js`
contract. Use the Fetch API with a five-second timeout, `textContent` for
service-provided values, and independent loading/error states for wardrobe and
outfit features. Use four client-side sections for Home, Weather, Add an item,
and My clothes. Keep recommendation and forecast states explicit until those
service endpoints are available. Store the selected clothing color as a hex
string and choose foreground text by luminance for readable item swatches.
Keep the UI dependency-free and responsive, with CSS custom properties for the
theme and a system dark-mode variant.

**Alternatives**
- Add a frontend framework and build step (rejected: unnecessary for this
  product and conflicts with the static deployment contract).
- Proxy both APIs through the UI host (rejected: adds infrastructure and hides
  the independently-failing service boundary).

**Consequences**
- The UI can be deployed without installing frontend dependencies.
- API validation and service errors are surfaced as friendly messages.
- The browser still depends on correctly configured CORS and the CD-generated
  Azure URLs.

## 3. Monitoring: stdout request metrics and one SLO

**Date:** 2026-11-24
**Owner:** Nikita

**Context**
The rubric requires request count, error rate, response-time percentiles, and
one measurable SLO for the two Container Apps without adding another service.

**Decision**
Use the existing one-line request logs from both services and save KQL queries
over `ContainerAppConsoleLogs_CL` for request count, 5xx error rate, p50/p95
duration, and the SLO that 99% of wardrobe `GET /items` requests finish under
500 ms over seven days.

**Alternatives**
- Add application metrics or a third monitoring agent (rejected: out of scope
  and increases operational complexity).
- Measure only availability checks (rejected: health checks do not represent
  user request latency).

**Consequences**
- The queries are low-volume and use data already emitted by the services.
- The SLO excludes ingress and scale-to-zero cold-start time; those caveats are
  documented.
- The custom table column names must be confirmed in the target workspace before
  saving the queries.

## 4. Storage and data model

**Date:** 2026-11-24  
**Owner:** Jinin Aljayyousi

**Context**  
The brief requires each service to have its own database, a schema defined by versioned migration files applied on startup, SQL Server in compose locally and serverless Azure SQL with auto-pause in production. Tests and CI must never touch the Azure database. A paused serverless database can take up to a minute to answer its first connection.

**Decision**  
- One database per service: `items` lives in the wardrobe database and `wears` in the outfit database. Locally they are two databases on one SQL Server container, created by a `db-init` step in `docker-compose.yml`.
- Plain numbered SQL files in `services/<service>/migrations/`, applied in name order on startup and recorded in `dbo.schema_migrations`. A failed migration is rolled back and stops the service from starting.
- `pyodbc` with Microsoft's ODBC Driver 18 and hand-written, parameterized SQL. No ORM.
- The connection is built from `DB_HOST`, `DB_NAME`, `DB_USER` and `DB_PASSWORD`, the same variables `infra/setup.sh` sets, always encrypted.
- Startup retries the connection for about a minute so the CD `/health` check survives a paused database. Each request makes a single attempt and returns a clear 503 if the database is down, instead of hanging.
- The item rules (category list, warmth 1 to 5, price 0 or more, required name and color) are checked twice: by Pydantic for a clear 422, and by `CHECK` constraints so bad data can never reach the table.
- `wears.item_id` refers to `items.id` without a foreign key, since the tables are in different databases. See [data-model.md](data-model.md).

**Alternatives**  
- One shared database for both services (rejected: the brief requires one per service, and it would couple the services).
- SQLAlchemy with Alembic migrations (rejected: more to learn and review for two small tables, and plain SQL files are easier to read in a pull request).
- `pymssql` instead of `pyodbc` (no system driver needed, but the outfit service already used `pyodbc`, and one driver for both keeps the Dockerfiles the same).

**Consequences**  
- The schema is easy to review, and every change is a new migration file.
- Deleting an item leaves its wears behind. The stats ignore wears for items that no longer exist, so they never show up.
- The ODBC driver makes the images larger and needs an apt step in each Dockerfile.
- The first request after the database auto-pauses can take several seconds or return a 503, which the SLO in section 3 excludes as a cold start.
